\section{Sprint 2: From Program Specification to Class Diagram}

This sprint turns the program specification of Sønderborg's digital media platform into a design. We first define the requirements, then perform a verb-noun analysis of the specification, derive CRC cards from both, and finally combine everything into a UML class diagram.

\textbf{Scope.} The design covers the core of the specification: seven media types, three user categories, borrowing and rating, collection and user management, and a console interface that asks for the user's role on startup. Authentication, returning items, sorting and file persistence are workshop extensions. They are not required for the core, but the design is prepared for them (e.g.\ the \texttt{CsvFileHandler} in the data access layer).

\subsection{UML class diagram}
% ---------------------------------------------------------------------

The class diagram is split over two pages to keep it readable. Figure~\ref{fig:media} shows the media model and Figure~\ref{fig:system} shows users, library, console interface and data access. \texttt{Media} and \texttt{Borrower} appear in both figures (collapsed in the one where they are not the focus), which connects the two parts. The main design decisions are:

\begin{itemize}
  \item \textbf{Abstract base class for media.} \texttt{Media} holds the state and logic that all media share (id, title, borrowers, ratings, download). The seven media types are subclasses that add their own attributes and actions, so a new media type is just a new subclass (NFR1).
  \item \textbf{Capability interfaces instead of deep inheritance.} Each verb from the analysis became a small interface (\texttt{IReadable}, \texttt{IWatchable}, \texttt{IPlayable}, \ldots). A class gets exactly the capabilities that fit it, e.g.\ \texttt{Podcast} is \texttt{IPlayable} and \texttt{ICompletable}, but not \texttt{IExecutable}. \texttt{IBorrowable}, \texttt{IRatable} and \texttt{IDownloadable} are implemented by \texttt{Media} because the specification allows all media to be borrowed, rated and downloaded.
  \item \textbf{Rating rule in the domain.} \texttt{Media.Rate()} checks that the rating user has borrowed the item and throws an exception otherwise (FR6, NFR4).
  \item \textbf{User hierarchy.} \texttt{Borrower} and \texttt{Employee} extend the abstract \texttt{User}; \texttt{Admin} extends \texttt{Employee} since an admin has all rights of an employee (FR13). Managing the collection and managing users are capabilities (\texttt{ICollectionManager}, \texttt{IUserManager}), which makes it possible to add new roles later (NFR2).
  \item \textbf{Three layers.} The presentation layer (\texttt{ConsoleUI}, the menus and \texttt{InputValidator}) only depends on the domain layer, and the domain layer (media, users, \texttt{Library}) never touches the console (NFR5, NFR6). \texttt{CsvFileHandler} is the data access layer.
  \item \textbf{One menu per role.} \texttt{AdminMenu} extends \texttt{EmployeeMenu} in the same way as \texttt{Admin} extends \texttt{Employee}, so users only see the actions their role allows (FR15).
\end{itemize}

Getters and setters (C\# properties), constructors and trivial helper methods are left out of the diagrams. Abstract classes and operations are written in italics, and the colours only group the elements: blue for media, cyan for presentation, green for domain, orange for data access, and yellow for interfaces.
